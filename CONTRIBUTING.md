## Requirements

- Windows 10 or 11, 64-bit.
- A stable Rust toolchain for the Microsoft Visual C++ (MSVC) target, with the Visual Studio Build Tools. Make it the default toolchain of the machine that runs the tests. The version resources of the programs are linked only for that target. On a GNU's Not Unix (GNU) toolchain the check G39 cannot run. It prints a `NOTICE` line to standard error when it is skipped. That line shows on a plain `cargo test`. It fails instead when `CI` or `PROCESS_TREE_GUARD_REQUIRE_RESOURCES` is set. Set the second one on your machine. The suite then covers the resources.
- Git Bash, Windows PowerShell and `cmd.exe`, which the tests use.

The library and the programs build with the Rust version that `rust-version` in `Cargo.toml` declares. The continuous integration job `minimum-rust` checks that on every change. The tests are run with the current stable toolchain only. A change that needs a newer Rust raises `rust-version` in the same commit. The change says so in the changelog.

## Rules for changes

- `cargo test --release` passes. On a busy machine, `PROCESS_TREE_GUARD_TIMING=info` reports the timing bounds instead of asserting them. Say so in the pull request if you used it.
- A change adds no compiler warning; the continuous integration check step denies warnings.
- No new dependencies. The guard uses only the Rust standard library and direct Windows system calls. Every line of code that runs is in this repository. No dependency has a source that a reviewer must also trust or read.
- A change in behaviour comes with a test. A new check gets the next identifier in its series (`G`, `U`, `B` or `A`). The check gets a row in `tests/PARITY.md`.
- Tests take every program from the binaries cargo built in the run (`CARGO_BIN_EXE_*`). Tests never take a program by a file name in the build folder. A stale file left there is never picked up.
- Tests do not depend on the file name of the built guard. They copy it to the names they need (`process-tree-guard` and the earlier name `process-guard`, accepted as an alias, each with an `-auto` copy where the check needs one) in a temporary folder.
- The README is updated when a flag, exit code, guarantee or limit changes.
- No test shows a prompt to the person who runs the suite.
- A run over the default cap (`--max-extension` over 21600) in a test says `--authenticate console` on the same line. The run has a standard input that is null, a pipe or a file. Check G93 scans the test sources for one that does not. The helpers that start a guard refuse a cap that a test builds when it runs.
- No test makes a request for Windows Hello or shows the credential dialog. A scripted consent stands in for Windows Hello in the unit tests. The only calls of Windows Hello made for real are two. One asks whether Windows Hello is available. One creates its owner window, which shows nothing. The window is made only on a window station that is not visible.
- G95 and G103 are the tests that use the desktop method. They do so on a window station that is not visible. The test helper makes that station and checks it first. They are also the tests whose failure mode is a real prompt. If the guard's test for a window station that is not visible were defective, a real prompt could appear. The secure prompt could appear on the desktop of whoever runs the suite. The prompt of Windows Hello could appear there. No record establishes where it would appear.
- G95 and G103 therefore run only when `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST` is set. Set it by hand where a person is signed in; no workflow sets it. `CI` alone does not. `CI` is also set on machines where a person sits. The two tests report NOT ASSERTED otherwise. Their helper waits only ten seconds for a refusal that is immediate. Step 11 of the manual check runs each once with the screen watched.
- G95, G97, G98 and G103 also report NOT ASSERTED where the host cannot make a window station. They also report it where the host cannot make a pseudo console. They report NOT ASSERTED unless `PROCESS_TREE_GUARD_REQUIRE_WINDOW_STATION` or `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set. Set those two by hand; no workflow sets them.
- G97 and G98 are the two tests that use the console method for real. They do it in a pseudo console that the test helper makes. No logon is ever tried in that console. G97 answers every question with an empty line. G98 types nothing while the process that started the guard exits.
- Both take the lock that the prompts of a Windows session share, and wait for it. They take a turn that every suite of the session shares. They try again for a minute when a real prompt holds the lock. They also try again when a guard that was refused less than 10 seconds before holds the lock. They are then reported NOT ASSERTED. They fail instead where `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set. Do not run two test suites at the same time in one Windows session. Do not run a step of the manual check at that time either. The prompts of the guard share one lock per session.
- A guard that another guard started is refused before its window station or its console is looked at. The refusal comes by the file names above it or by the job it is in. When the suite is run under a guard (`process-guard -- cargo test`, or a shell wrapped by the automatic wrapper), a refusal rule applies. Four tests report NOT ASSERTED. Those tests are G95, G97, G98 and G103. They fail instead where their variable is set. The other runs over the cap are refused for the guard above them. They are not refused for their standard input. G94, G99, G100, U25 and A42 assert that refusal in any surroundings.
- Cargo puts the tests it runs in a job. That job kills them when it closes. A guard takes that job for the job of a guard. Each test program therefore puts its own process in a job of its own. That job kills nothing. The job is nested in the job that cargo made. The test program does this before it starts a guard (`leave_the_job_of_the_runner` in `tests/common/mod.rs`).
- Five unit tests in `src/auth/tests.rs` run a copy of the test executable. They make checks that need no prompt. The checks hold under any guard. One checks the detection of a window station that is not visible. It also checks the refusal of the seat of the credential dialog there, on one of its own stations. One makes a buffer for a secret in a copy that nothing else has set up. It sees a panic zero that buffer. One begins the console prompt with a standard input that is not a console. It sees the prompt refused before anything is written. One puts a copy in a job of its own. It does so with the limit of a job of the guard, and without it. It checks that only the first job is taken for the job of a guard. One makes the owner window of the request for Windows Hello. It serves that window and destroys it. It does so on a desktop of a window station of its own that is not visible.
- Run the suite from a terminal that is not under a guard to assert the rest.

## Manual check of the prompts

The tests do not exercise two prompts with a real password or a real request. One is the sign-in prompt for a cap over the default. The other is the prompt of Windows Hello. Three cases are the exceptions. One is the refusal on a window station that is not visible (G95, G103). One is the console prompt in a pseudo console with empty answers (G97). One is the same prompt left unanswered in a pseudo console while its starter exits (G98).

Before a release that changes `src/auth.rs` or `src/sys.rs`, run these steps on a machine where someone is present. Sign in with an account that has a password. Run the steps from the interactive desktop. Steps 9 and 10 are the exceptions. Step 12 needs an account for which Windows Hello is set up. Run them in a terminal that is not under a guard. Run them in a terminal that is not in a job. That job must not kill its processes when it closes. A guard that another guard started is refused before anything is shown.

Use a short command, for example `cmd /c echo ran`, and a deadline under 30 seconds. Write down what you see where a step says so. The documents say what is expected. The steps confirm it.

The desktop method asks Windows Hello first. It shows the credential dialog only where Windows Hello is not available. Steps 1 to 5, 7 and 10 exercise the credential dialog. Run them with an account that has no Personal Identification Number (PIN), fingerprint or face set up. Or run them in a virtual machine on which Windows Hello cannot be set up. Confirm that the reason of each line of the log ends with `(Windows Hello was not available: NAME)`. Step 4 is the exception. It needs a PIN with Windows Hello disabled by a policy. Where Windows Hello is available the same command asks Windows Hello instead (step 12). Step 6 uses `--authenticate console` and needs no such account.

1. Desktop prompt (the credential dialog), right password: `process-tree-guard --extendable --max-extension 86400 --timeout 20 -- cmd /c echo ran`. A secure desktop prompt appears, captioned Process Tree Guard.
- It names first the command line, the program, and the account whose password it asks for. It names the parent process as the system reports it, the nearest one. It names each in square brackets. Then it says that the processes of the run may each ask to keep it alive. Each may ask for up to 24 hours at a time. Each may renew without a total limit. It says that the run starts with a deadline of 20 seconds. It lists only your account.
- The pass criterion for the text is that the Command line field is fully visible in the dialog. If the dialog clips the text, write down where it is clipped. Write down which field is the last one shown.
- Enter the password. The command prints `ran`, and the log has one `decision=exception-approved` line with `attempt=1`.
- Record the result for each type of account you can try. The types are a local account, a Microsoft account, a domain account. The password that the secure prompt returns must be accepted. The prompt can return it in clear text. The prompt can return it in a protected form that the guard unprotects. If the run is refused, the reason can be that the protected form could not be unprotected. Then the credential dialog cannot approve for that type of account. The documents must say so before a release.
- Run it a second time with `--shell cmd --command-b64 TEXT`, where TEXT is the Base64 of `echo a && b %PATH% ` followed by 300 letters x (in PowerShell: `[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("echo a && b %PATH% " + ("x" * 300)))`).
- The text is given as Base64 because a shell changes `&&` and `%PATH%` on the command line before the guard sees them.
- Write down what the dialog shows. Write down whether `&&` and `%PATH%` appear as typed. If the dialog consumes an ampersand, the display must be fixed. Fix it by doubling the ampersand for the dialog only. Write down that the command line ends with how many characters were left out.
- Run it a third time with a copy of `cmd.exe`. The name of the copy begins with the Cyrillic letter U+0441, so that it looks like `cmd.exe`. Confirm that the dialog shows that letter written as `\u{441}`. Confirm that the dialog shows the note about characters outside basic Latin. Confirm that the dialog does not show the letter as a letter.
- Some hosts put their terminal in a job that kills its processes when it closes. Editor terminals and continuous integration runners are examples. Where you have such a host, run the command from that terminal too. Confirm that the command is refused with 125. Confirm that the reason is that another guard started it. Confirm that no prompt appears.
2. Wrong password three times: repeat, and enter a wrong password each time.
- After the second and third, the prompt shows that the user name or password is incorrect. The second and third prompt are shown. They are not cancelled at once. All the calls of the prompt are made on one thread. This is the only step that shows it for the desktop method.
- The run exits with 125 after the third. The command never runs. The log has `decision=exception-refused` with `attempt=1`, `attempt=2` and `attempt=3`. The last one says that no attempts are left.
- Do this once only: each failure counts toward the lockout of the account.
3. Cancel: repeat and cancel. The run exits with 125 and the log has one refusal with `attempt=1` that says the prompt was cancelled.
4. PIN at the credential dialog. A PIN is set up, but Windows Hello is disabled by a policy or does not answer. The dialog is shown. Repeat the command. Choose the PIN tile and enter the PIN. Where Windows Hello is available, the PIN is entered in its prompt (see step 12).
- One of three things happens. The answer unpacks to a name and a password in a protected form. The guard unprotects that form, and the logon is tried. The password is sent to `LogonUserW` if the name is the account's own. The password counts toward the lockout. Or the answer unpacks to clear text, and the logon is tried in the same way. Or the answer does not unpack. Then the log has an attempt with a stated reason. The reason is that the answer could not be read as a user name and a password. An answer that does not unpack counts as an attempt. A logon that the system refuses counts as an attempt. The prompt is shown again.
- Write down which one happens. The documents say only that a PIN may be answered with the password in a protected form.
- If the account has a smart card, choose it. Record that it counts as a failed attempt in the same way.
5. No answer, and a starter that goes, at the credential dialog. The same for Windows Hello is in step 12. Repeat the command and leave the prompt alone.
- After 300 seconds the run exits with 125 ("no answer within 300 seconds"). Look at the screen once the guard has exited, and write down whether the dialog is gone or still there. The documents do not claim that it goes until this step has been run. The guard exits as soon as the 300 seconds are over. It exits without the 10 seconds of waiting that follow another refusal. The dialog must not stay open for any time after the error is printed. If a password can still be typed into it, record that.
- Then start the guard from a `cmd.exe` window. While the prompt is open, end that `cmd.exe` in Task Manager. Within a second the run is refused ("the process that started the run exited"). The log has `attempt=1`. The prompt should go. Write down what happens to the dialog.
6. Console prompt: from a real terminal, run the same command with `--authenticate console`.
- The message is written to the console once. Then the prompt asks for the password alone. The prompt names your account. Write down the form of the name. Confirm that no question for a user name is asked. The right password runs the command.
- Run it again and try Esc, then Ctrl+C, then Ctrl+Z and Enter. Write down what each one does. The documents do not claim a result for these keys until this step has been run. Esc and Ctrl+Z with Enter may leave the prompt waiting. They may give an empty answer that uses an attempt. Ctrl+C may end the guard, which also refuses the run. The message tells the user how to refuse the run. Leave the prompt unanswered for 300 seconds. Or close the console.
- Store a generic credential with `cmdkey /generic:"Process Tree Guard" /user:x /pass:y`. Run the console method again. Confirm that the prompt is still shown. Confirm that the prompt does not return the stored credential. Delete it with `cmdkey /delete:"Process Tree Guard"`.
- Run it again with standard input piped (`echo x | process-tree-guard ...`). Confirm that it is refused with 125. Confirm that a reason names standard input. Confirm that no prompt appears.
- Command history: the guard clears the command history that the console keeps for its own executable name. It clears it after every console prompt. Run a console prompt and answer it with a known test password. In the same console, press F7. Run `doskey /history`. Read the history kept for `process-tree-guard.exe`. Read it with `GetConsoleCommandHistoryW`, for example. Or run the guard again and read the F7 popup. Record whether any password line is present. A line that is present means the call is missing. It can also mean that the call does not clear the history. Either is a defect to be fixed.
- Ctrl+C: run the console method again. Press Ctrl+C while the prompt waits for the password. Confirm that the shell echoes the characters you type afterwards. The guard puts the console mode back on a control event while the prompt reads. An echo-off shell is therefore a defect. Ending the guard from Task Manager is outside this. It may leave the mode as it was set.
- Finally let the console prompt time out. Leave it alone for 300 seconds. Or end the process that started the guard while it is open. Confirm that the shell echoes the characters you type afterwards. If it does not, the console mode was not restored. Type `cmd /c echo on` or open a new window. Report it.
7. Microsoft account and Azure Active Directory (Azure AD) work or school account. Use a machine signed in with a Microsoft account. Use one signed in with an Azure AD account. Repeat step 1 on each.
- The prompt returns a user name. For a Microsoft account, the name is `MicrosoftAccount\name@example.com` or the local account name. For an Azure AD account, the name is `AzureAD\Name`. Confirm that `LogonUserW` accepts the name. Write down the form of the name that came back in each case.
- If it is not accepted, the run is refused after three attempts. Each attempt counts toward lockout. The form of the name must be changed. For an Azure AD account, pass the user principal name with a null domain.
8. Nothing at or below the cap prompts: run `process-tree-guard --extendable --max-extension 21600 --timeout 20 -- cmd /c echo ran` and confirm that no prompt appears and the command prints `ran`.
9. Nobody present: run the step 1 command with `--authenticate desktop` and a deadline under 30 seconds. Run it (a) from a scheduled task. The task is set to run whether or not the user is logged on. Run it (b) over a Secure Shell (SSH) or Windows Remote Management (WinRM) session.
- Record that each exits 125 at once. Record that the reason has "session 0" or "no interactive window station" in it. Record that no dialog appears on the desktop. Record that the command does not run. The README names only what this step confirms.
- The reason can instead be that another guard started the run. Then the host put the shell in a job that kills on close. The step has not exercised the test for a person being present.
- Record that. Try a host whose shell is not in such a job. Or rely on the unit tests of the test for a person being present, and on G95.
10. Domain controller out of reach. Use a machine that is joined to a domain. Sign in with a domain account. Disconnect the machine from its domain controller (the network off). Repeat step 1. Write down whether the name that the prompt returns is accepted. The look up must accept it. `LogonUserW` must accept it. If the run is refused with a look up error, one thing must change. The documents' statement about the form of the name must be changed.
11. The tests on a window station that is not visible (G95 and G103), watched. Keep the screen in view. Set `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST=1`. In a Command Prompt, run `set PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST=1`. Then run `cargo test --release --test guard g95 -- --nocapture` once. Run `cargo test --release --test guard g103 -- --nocapture` once. Use a machine where someone is present. The desktop must be unlocked.
- Record that nothing appears on the desktop. Record that no credential dialog appears. Record that no prompt of Windows Hello appears. Record that the tests pass. A line NOT ASSERTED means the variable was not seen.
- The test asserts one reason. The process has no interactive window station. Or the test process runs in session 0, and the test asserts that reason. A host whose test process runs in session 0 is a build agent installed as a service. The guard reports the session 0 reason first.
- If a prompt appears, record where. The places are the desktop, the secure desktop, or nowhere. End the test. Treat the guard's test for a window station that is not visible as defective. G95 and G103 are the tests whose failure mode is a real prompt. No record establishes where such a prompt would appear. This step's run establishes it.
12. Windows Hello. Use an account for which Windows Hello is set up: a PIN, a fingerprint or a face. Run from the interactive desktop. Run one run at a time. Run in a terminal that is not under a guard: `process-tree-guard --extendable --max-extension 86400 --timeout 20 -- cmd /c echo ran`.
- Approve: the prompt of Windows Hello appears, with the message of the guard in it. Verify with the PIN, the fingerprint or the face. The command prints `ran`. The log has one `decision=exception-approved` line. That line has `method="hello"` and `attempt=1`. That line has the reason that Windows Hello verified the signed-in user.
- A second request: once the first run has ended, run the same command again. Run it once more. An approval keeps no cool-down. Only a refusal keeps one. Write down whether the prompt appears for each run. Write down whether it asks again for each run. The system can reuse a recent verification. Then a run is approved with no prompt. That approval shows no presence at the moment of the request. The default method must not rely on Windows Hello until that is mended.
- Face and fingerprint: use a device with face recognition. Start the command with your face toward the camera. Keep your hands off the keyboard. Write down whether the prompt verifies by itself, with no act by you. If it does, presence alone approves the run, as SECURITY.md says. Use a device with a fingerprint reader. Write down whether the prompt waits for a touch.
- Read the whole message in the prompt. Write down where it is clipped, if it is. It must show the sentence that begins it, without scrolling. That sentence is `Process Tree Guard asks Windows Hello to allow this run; cancel to refuse it.` It must show the command line. It should show the closing `Cancel to refuse it.` If the end is clipped, write down one thing. Write down which field is the last one shown. Adjust `HELLO_MESSAGE_LIMIT` and the limits of the fields in `src/auth.rs` before a release.
- A long command: run it again with `--shell cmd --command-b64 TEXT`. TEXT is the Base64 of `echo a && b %PATH% ` followed by 300 letters x. That text is the command of step 1. Use a program in a folder whose path is 200 characters long. Write down three things. The command line ends with how many characters were left out. `&&` and `%PATH%` appear as typed. The words that say how to refuse are visible.
- Placement: write down where the prompt comes. It can come in front of the other windows or behind them. The owner window of the guard is never shown. Write down whether the prompt takes the focus. Try it from Windows Terminal. Try it from a plain console window. Try it with another program maximized. The prompt can be behind a window. Then build the alternative and repeat this step. The alternative is a layered window that is shown without being activated, then `SetForegroundWindow`. Do not build it unless this step needs it. Write down also whether the screen dims. The screen dims for the secure desktop. The documents say Windows Hello is not known to use that desktop.
- Cancel: repeat and cancel the prompt. The run exits with 125, the command never runs, and the log has one refusal with `method="hello"`, `attempt=1` and the reason `Windows Hello did not verify the user: Canceled`.
- A wrong PIN until `RetriesExhausted`: repeat and enter a wrong PIN until the system asks no more. Do it once only. Use a machine where you can sign in with the password afterwards. Windows Hello and the Trusted Platform Module keep their own count. They may lock the PIN. Write down the reason in the log (expected `RetriesExhausted`). Write down what the prompt did. Confirm that the credential dialog is not shown afterwards.
- No answer: repeat and leave the prompt alone. After 300 seconds the run exits with 125. The reason is `no answer within 300 seconds, the request was cancelled`. Look at the screen once the guard has exited. Write down whether the prompt is gone. Write down how long it took. The documents do not claim that it goes until this step has been run. The prompt can stay. A PIN can still be entered into it. Record that if it happens.
- The guard ended from outside: repeat. While the prompt is open, end `process-tree-guard.exe` in Task Manager. Write down whether the prompt closes with the process or stays. Then repeat. Start the guard from a `cmd.exe` window. End that `cmd.exe` while the prompt is open. Within a second the run is refused (`the process that started the run exited`, `attempt=1`). The request is cancelled. The prompt should go. Write down what happens to it.
- Windows Hello not set up: use an account with no PIN, fingerprint or face. Or use a virtual machine. Run the same command. The credential dialog appears. It lists only the current user. The dialog returns a password in clear text or in a protected form. That password is accepted. The log lines have `method="desktop"`. They end with `(Windows Hello was not available: NotConfiguredForUser)`. Or they end with the name that the system gives for the case. The names are `DeviceNotPresent` and `DisabledByPolicy`. A policy can disable Windows Hello. Where one can, repeat with it disabled. Write down the name.
- A PIN-only account in the fallback. An account signs in with a PIN alone. Windows Hello is disabled by policy. The dialog offers the PIN. Write down whether the answer is accepted. The answer can be a protected form that unprotects. The answer can be refused. The reason then is that the protected form could not be unprotected. The answer can be impossible to give.
- Not the desktop in front: in a `cmd.exe` window run `timeout /t 15 /nobreak >nul & process-tree-guard --extendable --max-extension 86400 --timeout 20 -- cmd /c echo ran`. Lock the screen at once with the Windows key and L. When the guard has run, unlock and read the log. The run is refused with 125, `method="hello"` and `attempt=0`. The reason is that the desktop that receives the input of the user cannot be opened. The screen may be locked. No prompt of Windows Hello was shown. The credential dialog was not shown. Then start the command from a desktop that a program made. An example is the Sysinternals Desktops tool. The reason says to start the run on the desktop that the user is looking at. Write down any host with one property. On that host, the guard is refused for this reason. The desktop is unlocked. The user is looking at that desktop. The check would then be wrong there.
- Another account: sign in as one account. Start the guard as another account. Windows Hello is set up for that account as well. Use `runas /user:OTHER` with a command prompt of that account, in the session of the first. Windows Hello may not be set up for OTHER. Then the credential dialog asks for the password of OTHER. That is the right behaviour. Run the step again with an account that has Windows Hello. The run is refused at once with 125, `method="hello"` and `attempt=0`. The reason names both accounts. The reason says that Windows Hello verifies only the signed-in user. No prompt of Windows Hello is shown. No credential dialog is shown.
- A Remote Desktop session: from a Remote Desktop session of the user, run the command. Write down the availability that the log gives (`Windows Hello was not available: ...`). Or write down the prompt that appears. Write down that the run is decided in the same way as at the console.
