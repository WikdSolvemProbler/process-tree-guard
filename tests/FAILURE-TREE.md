# Failure-tree map

Every branch of the guard's failure tree, mapped to the test family
that covers it. A branch with no family is named as unimplemented —
the map is the suite's honest coverage statement, not a claim.
"Implemented" means runnable test code exists in `tests/`; most
guard-driving families execute on Windows against the built package
(their tier), while the harness-logic and battery-audit families
execute anywhere.

The guard's own in-tree Rust tests (437 counted once, in the tree's
`src/` unit tests and `tests/` parity checks) are not recounted here;
this suite's counted-once total is its own Python tests: 647 tests counted once, reported by
`run_tests.py` and in the README.

**Scope decision — the cap-over-default approval flow.** The
flow's non-interactive seams are already under automated test
in the tree, and this suite adds no duplicate family:
`src/auth/tests.rs` drives `authorize_with` and `decide` through
the `auth::seam` stub prompt and verifier — the cap arithmetic
and the hours figure rounded up from the cap, the refusal paths
(a nested run, a run another guard started, the starter gone, a
prompt never shown, an approval that cannot be recorded), and
the prompt message's escaping and field limits — and the tree's
parity checks G93–G103 run real over-cap invocations that refuse
before anyone is asked on non-console input, exercise the
desktop method on a non-visible window station (G95, G103) and
the console method in a pseudo console (G97, G98). What no
automation in either tree exercises is a real Windows Hello
request or a real password typed at the credential dialog or
the console prompt: those need a person present on an
interactive desktop, and a suite family that invoked them would
either block the unattended run on a live prompt or test only
the refusals already asserted in-tree. That remainder is
therefore not automatable in this suite. Its revival instrument
is the manual check in the tree's `CONTRIBUTING.md` ("Manual
check of the prompts"): it is run, by a person present on an
interactive Windows desktop, before any release that changes
`src/auth.rs` or `src/sys.rs` — for this package, as part of
Peter's local Windows run. For this package the check is
formalized as the recorded manual instrument
`usability-evidence.json` at the package root — one record per
prompt class (the Windows Hello request, the credential dialog,
the console password prompt), each carrying what was exercised,
what the operator observed and the outcome per class — which is
profile dimension (8)'s collecting instrument in the campaign
configuration, at manual/Windows-theory tier. Until that run, the interactive
remainder stands at manual/Windows-theory tier; nothing in this
suite claims it as measured.
